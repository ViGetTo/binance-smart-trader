# Binance Smart Trader

Локальный Python 3.12+ проект для автономной **виртуальной** торговли Binance Spot:
Adaptive Momentum Breakout, Trend Pullback, New Listings Hunter, независимый Risk Manager, PAPER,
Binance Spot DEMO, исторический BACKTEST, SQLite, Streamlit и Telegram.

**Android / Termux:** готовая установка и запуск одной командой `trade` —
[инструкция для Termux](docs/TERMUX.md). Репозиторий: https://github.com/ViGetTo/binance-smart-trader.

**Реального торгового режима нет.** Подписанные запросы разрешены только на точный адрес
`https://demo-api.binance.com/api`; production-клиент принимает только публичные GET и
не принимает ключи. Редиректы запрещены. `.env` содержит только ключи Demo и Telegram.

Проект реализует рабочий контур получения данных и принятия решений; это первая версия,
проверенная локальными автоматическими тестами. Исполнение с настоящими Demo-ключами
требует проверки в доступном регионе. Из среды разработки публичный и Demo endpoints
вернули **HTTP 451**. Реальные Binance-сделки, исторический рыночный бэктест и 30–60 дней
форвард-наблюдений здесь не проводились. Синтетический пример ниже проверяет механику,
его результаты не являются исследованием доходности.

Архитектура и порядок восстановления: [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).
API-источники и ограничения: [docs/API.md](docs/API.md).

## PAPER Lab v0.3: три независимых счёта

**Исправление v0.3.1:** если после настройки остаётся Demo-экран, выполните из каталога
проекта `git pull --ff-only`, затем `bash scripts/trade-termux.sh paper`. Это прямой переход
на три PAPER-счёта без меню/ключей/переустановки зависимостей. Открытая панель теперь
перечитывает выбранный профиль; сохранённый PAPER не перекрывается старым окружением Termux.

По умолчанию запускаются **три локальных PAPER-счёта по 4900 виртуальных USDT**, без ключей
и верификации. Публичные цены/свечи/стакан Binance настоящие; исполнения виртуальные.
Счета параллельно используют общий GET-клиент с rate limiter и один WebSocket:

| Счёт | Риск сделки | Максимальное размещение | Поиск сигнала |
|---|---:|---:|---|
| Базовый | 0.5% | 25% | Строгие правила на 15m |
| Рискованный | 2% | 75% | 15m, объём 1.4×, цель 3.5R |
| Активный | 0.3% | 40% | 5m, 12 свечей, объём 1.2×, скан каждую минуту |

Издержки одинаковые; баланс, позиции, риск, выбор стратегий и история каждого счёта независимы.
Все сохраняют BTC/ликвидность/стоп-фильтры; максимум 3 позиции. Новые листинги во всех
профилях сохраняют 15m, наблюдение 24h, 4h диапазон и жёсткие лимиты 0.2% / 5%.
Рискованный профиль может потерять больше; частые сигналы не означают обязательные сделки.
Параметры профилей: `[paper_profiles.*]` в `config.toml`. Смена стартового баланса не пополняет
существующие счета. Исторический движок по-прежнему использует 15m: результаты 5m профиля
оцениваются отдельно в PAPER, его полноценный 5m бэктест здесь не заявлен.

В Termux: `trade` → оставить сервис на ночь → утром `trade report`. `Q` закрывает только
панель. `B/A/T` выбирают счёт, `0` открывает сравнение. Отчёт с открытым PnL, просадкой,
сделками и издержками сохраняется в `data/reports/paper-comparison.json` каждые 30 секунд.
Одна ночь не является доказательством прибыльности.

`trade config`: **1 → 1** отключает Binance-аккаунт и включает PAPER; **1 → 3** отключает
также публичные котировки (торговля приостанавливается). **6** управляет автообновлением.
Перед запуском `trade` проверяет GitHub, устанавливает обновление только при остановленной
сессии, сохраняя `.env` и базы. Подробные команды обновления и ночного запуска:
[docs/TERMUX.md](docs/TERMUX.md).

## Быстрый запуск: Linux / macOS

```bash
cd binance-smart-trader
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -e '.[test]'
cp .env.example .env
python -m smart_trader.terminal config
smart-trader check
pytest -q
smart-trader run
```

В другом терминале из этого же каталога:

```bash
source .venv/bin/activate
streamlit run dashboard.py --server.address=127.0.0.1
```

Панель: http://127.0.0.1:8501. По умолчанию PAPER Lab; ключи не требуются.
Терминальная панель: `python -m smart_trader.terminal ui`. Она не зависит от сайта.
Для краткого сравнения: `python -m smart_trader.terminal report`.
Бот сканирует весь подходящий USDT Spot universe; первоначальная проверка возраста всех
рынков занимает несколько минут. Отсутствие сделок при невыполненных фильтрах нормально.

`smart-trader run --once` выполняет один анализ без новых ордеров; открытые позиции из БД
сверяются при старте. Для торговли и постоянной PAPER-защиты нужен обычный `run`.

## Подключение настоящего Binance Spot Demo API

1. Откройте [официальный Binance Demo API Management](https://demo.binance.com/en/my/settings/api-management)
   из своего Binance Demo аккаунта. Создайте Demo API key с разрешением Spot trading.
   Текущий адаптер использует HMAC SHA256, поэтому нужен HMAC key/secret.
2. В `.env` задайте:

   ```dotenv
   TRADER_MODE=DEMO
   BINANCE_ENABLED=true
   TRADER_DB=data/demo.sqlite
   TRADER_PAPER_LAB=false
   BINANCE_DEMO_API_KEY=your_demo_key
   BINANCE_DEMO_API_SECRET=your_demo_secret
   ```

3. Проверьте виртуальные USDT и разрешения в Demo UI. `smart-trader check` проверяет только
   общедоступное соединение, без передачи ключей. Затем запустите `smart-trader run`.
4. В панели проверьте DEMO, heartbeat, состояние соединения, решения и `venue` сделок.
   Подписанные account/order запросы используют исключительно Demo-домен. Публичные данные
   для поиска возможностей берутся с production; исполнимые цены и правила DEMO перепроверяются
   на Demo непосредственно перед входом. Технический тест заявки `order/test` сам сделки не создаёт.

Binance может ограничивать доступ по региону, разрешениям, IP или на время обслуживания.
HTTP 451 не обходится. Ошибка аутентификации останавливает запуск; она не маскируется
автоматическими PAPER-сделками. Прямой запуск строгого DEMO при **отсутствующих** ключах
останавливается. Termux `trade` при отсутствии ключей явно переключает пустой остановленный
профиль в отдельный PAPER Lab и сообщает об этом. Если символ отсутствует на Demo, он
пропускается — PAPER fallback отключён. Исследовательский PAPER и прежнее поведение
доступны отдельно, но не выдаются за ордера аккаунта Binance.

Начальный капитал DEMO при первом подтверждённом запуске равен свободным USDT из
`GET /api/v3/account`. Например, при ответе API 4900 USDT риск 0.5% ограничен 24.50 USDT,
а общая стоимость позиций — 1225 USDT. Число 4900 не зашито в код. Учитывается собственная
торговая деятельность бота; фактические free/locked балансы API показываются отдельно.
Повторный запуск не обнуляет статистику и не сбрасывает капитал. Ручные пополнения, выводы
и сделки не объявляются прибылью стратегии; доступный капитал дополнительно ограничивается
актуальным свободным Demo USDT.

Мастер создаёт `data/demo-<отпечаток ключа>.sqlite`, сохраняя PAPER-историю отдельно.
Он не заменяет старую симуляцию биржевой историей и не выводит непроверенный баланс.
Менять Demo-ключи/профиль можно только после остановки и закрытия всех intents.
Не сбрасывайте Demo-счёт и не торгуйте вручную на нём во время работы бота: расхождение
балансов вызывает остановку входов.

## Логика и риск

Все настройки сигналов и риска находятся в `config.toml`. Веса нормируются ограниченными
percentile ranks, поэтому экстремальный показатель не может получить неограниченное влияние.
Рейтинг строится каждые 300 секунд; рассматриваются до 3 обычных кандидатов и один новый.
Ордера допускаются только при выполнении всех сигналов и финальной проверке риска.

Основная стратегия проверяет BTC 1H EMA50/200, EMA20/50 монеты, закрытый 15M breakout по
предыдущим 20 свечам, объём 1.7×, ATR, глубину, spread, отрыв от пробоя и net reward/risk ≥2.
Стоп 1.8 ATR(14), цель 2.5R. Рейтинг сам по себе не является торговым сигналом.

Trend Pullback требует того же BTC/1H trend filter, контролируемого касания EMA на 15M,
закрытого бычьего подтверждения выше предыдущего high, объёма 1.2× и ограниченного отрыва
от EMA относительно ATR. Риск, защиты и отсутствие усреднений общие.

Автовыбор `[selection]` сравнивает только прошлые закрытые сделки того же venue, доступные
до свечи сигнала. По умолчанию нужны 20 сделок и 30 дней; иначе сохраняется исходный
порядок сигналов, а не объявляется «найденная прибыльная стратегия». При достаточной
выборке используется нижняя оценка среднего R с поправкой на стандартную ошибку; если
верхняя оценка отрицательна, стратегия пропускается. Это исследовательская эвристика,
не статистическое доказательство доходности. Она не повышает риск, не принуждает сделки
ради набора данных и может выбрать отсутствие сделки. Сравнение за 90 дней и все пороги
доступны в конфигурации. Live, BACKTEST и walk-forward используют этот же причинный selector.


New Listings Hunter хранит `first_seen` и отдельный `earliest_ms` первой доступной 1M свечи.
Первые 24 часа — наблюдение и сохранение свечей, даже при малом объёме. Возраст 24–168 часов,
консолидация минимум 16×15M, breakout и объём 2×. EMA200/50 для новых рынков не требуется.
API не предоставляет достоверное универсальное поле времени листинга: первая свеча является
оценкой, особенно при релистинге/миграции. Официальные объявления автоматически не подтверждаются;
для исследования нужно сверить время с [официальными объявлениями](https://www.binance.com/en/support/announcement/new-cryptocurrency-listing?c=48).
Binance Alpha загружается отдельно как информационный список, который не участвует в Spot-исполнении.

Risk Manager проверяет 0.5% / 0.2% риска с расходами, 3 позиции, 25% суммарной стоимости,
5% размера новой монеты, дневной/недельный equity loss 2% / 5%, корреляцию и паузу 12 часов
после 3 убыточных сделок. При недостаточной истории корреляции второй актив не открывается.
Потери считаются от UTC начала дня/недели с учётом открытых позиций. При ошибке Risk Manager
входы отключаются. Панель может изменять лимиты без перезапуска, но не отменяет проверки.

Размеры и цены ордеров рассчитываются через `Decimal`. До Demo-входа проверяются LOT_SIZE,
MARKET_LOT_SIZE, PRICE_FILTER, MIN_NOTIONAL/NOTIONAL, ценовые процентные ограничения,
MAX_POSITION, число обычных/algo/order-list заявок, exchange-wide и account asset filters.
Неизвестный фильтр блокирует вход. Если взвешенная справочная цена имеет неподходящее окно
усреднения, вход отклоняется. Сервер остаётся окончательным арбитром динамических фильтров.

## Исполнение, перезапуск и Kill Switch

DEMO использует реально документированный OCO: SELL TAKE_PROFIT + STOP_LOSS с рыночным
исполнением при срабатывании. Это не stop-limit: стоп не оставляет лимитную заявку ниже рынка.
Проверяется поддержка OCO и типов ордеров, ответ списка и обе ветки. Рыночное исполнение
не гарантирует точную цену и максимальный убыток при гэпе. Фактические комиссии берутся из
`myTrades`, включая комиссии в базовом активе; комиссии в третьем активе переводятся в USDT
по текущей публичной avgPrice и являются оценкой конвертации. Частичные исполнения сверяются
до отмены остатка и установки защиты/закрытия.

Каждый сигнал имеет стабильный ID; intent и client order ID сохраняются **до** отправки.
При тайм-ауте POST не повторяется. Бот запрашивает состояние; даже «order not found» после
неизвестного результата не доказывает, что запрос не был исполнен. Такой intent остаётся
в карантине, новые входы остановлены. Если API никогда не подтвердит заявку, потребуется
проверка в Demo UI и восстановление состояния оператором; слепой повтор не производится.

Если OCO отклонён, бот останавливает входы и закрывает подтверждённый остаток. Если результат
создания/отмены неизвестен, сначала сверяется список и обе ветки, чтобы не отправить конфликтующий
SELL. При сетевой недоступности невозможно гарантировать немедленное закрытие. Монитор повторяет
сверку; ошибка одного символа не прекращает обслуживание остальных.

Остаток меньше LOT_SIZE/MIN_NOTIONAL хранится в позиции как `DUST` и блокирует дальнейшие
входы до разбирательства. Он не списывается как ноль и не объявляется полностью закрытой сделкой.
Это консервативное ограничение первой версии, особенно при комиссии в базовой валюте. Не выполняется
автоматическая конвертация dust, поскольку это другой API-механизм и не часть Spot OCO.

PAPER проходит по актуальному REST стакану, использует не более 5% каждого уровня и глубину
в заданной полосе, допускает частичное IOC-исполнение и добавляет комиссию/проскальзывание.
Для новых листингов проскальзывание выше. Это модель, не реальные Binance-исполнения.
PAPER stop/target требуют запущенного процесса и доступной сети; после простоя используется
следующая доступная цена, без выдуманного исполнения по историческому стопу.

```bash
smart-trader kill             # новые входы запрещены; защитные ордера/монитор работают
smart-trader kill --flatten   # также запросить отмену защиты и закрытие виртуальных позиций
smart-trader report
```

Команды записываются в SQLite; их выполняет работающий `run`. Пауза не завершает процесс.
Возобновление запрашивается в панели: исполнитель проверяет здоровье соединения, intents и
настройки. Убыточные дневные/недельные лимиты при этом продолжают действовать.
`Ctrl+C` завершает процесс: DEMO OCO остаётся на бирже, PAPER монитор останавливается.
Два исполнителя с одной БД запрещены OS lock. Запускайте только одного бота на выделенный Demo-счёт.
Для переноса/backup SQLite при работающем процессе используйте SQLite backup API, а не копию одного
`.sqlite` без WAL. Не удаляйте БД при открытых DEMO-ордерах.

## Telegram

Задайте `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID` в `.env`. Сначала начните диалог с вашим
ботом в Telegram. Уведомления: новые рынки, открытие с причиной/qty/stop/target/risk, закрытие
с причиной stop/target, лимиты, ошибки и ежедневный UTC отчёт. Сообщения проходят через
SQLite outbox и переживают перезапуск. После тайм-аута Telegram возможна повторная доставка:
Bot API не предоставляет идемпотентность `sendMessage`. Пустая конфигурация отключает отправку.
Ключи, request URLs и заголовки авторизации в журналы не выводятся.

## Исторические данные и бэктест

Загрузка идёт из официального Binance REST. Требуется включить BTCUSDT и минимум 201 час
истории до первого оцениваемого дня для прогрева EMA200.

```bash
smart-trader download --symbols BTCUSDT ETHUSDT SOLUSDT --start 2023-12-20 --end 2025-01-01 --output data/history
smart-trader backtest --data data/history --start 2024-01-01 --end 2025-01-01 --allow-modelled-liquidity --output reports/2024
smart-trader backtest --data data/history --allow-modelled-liquidity --walk-forward --train-days 60 --test-days 30 --sensitivity
```

Результаты: `report.json`, `trades.json`, `equity.csv`, по запросу `walk_forward.json` и
`sensitivity.json`. Режим BACKTEST также указан в enum; он запускается отдельной CLI-командой,
а не через бесконечный `run`.

`universe.json` хранит для каждого символа:

```json
{
  "symbols": {
    "BTCUSDT": {
      "listed_ms": 1502942400000,
      "delisted_ms": 9999999999999,
      "trading_intervals": [[1502942400000, 9999999999999]],
      "rules": [{"effective_ms": 0, "data": {"symbol": "BTCUSDT", "baseAsset": "BTC", "quoteAsset": "USDT", "status": "TRADING", "isSpotTradingAllowed": true, "filters": []}}],
      "assumed_spread": 0.001,
      "assumed_depth_usdt": 100000
    }
  }
}
```

Это схема, не готовый fixture: `filters` нужно заполнить настоящими ограничениями
exchangeInfo; обязательны PRICE_FILTER и LOT_SIZE. Downloader делает это автоматически.
CSV использует 12 официальных kline-полей, включая `quote_volume` и `close_ms`.

Downloader честно маркирует, что правила exchangeInfo **текущие** и только предполагаются
для прошлого. Он не может получить историю уже удалённой пары через текущий REST. Для
исследования полного universe добавьте архивные данные делистингов и датированные правила
в `rules`, `trading_intervals`. Бот сохраняет собственные снимки exchangeInfo при изменении и
полученные закрытые свечи в SQLite для последующего исследования. Текущий состав рынка
не выдаётся за исторический. Первая строка CSV не используется как дата листинга.

Бэктест раскрывает бары последовательно, сигнал из прошлого бара исполняется на следующем
open с модельным spread/slippage, 1H строится только из 4 полных 15M. В неоднозначном баре
stop исполняется раньше target, гэп вниз ухудшает стоп. Активные позиции закрываются на
конце окна с расходами; окончание данных предполагает ликвидацию по последней известной
цене и явно предупреждает, что реальный делистинг может оказаться хуже.

OHLCV не содержит bid/ask, глубины, очереди заявок и outage-событий, поэтому без явного
`--allow-modelled-liquidity` бэктест отказывается работать. Это исследовательский replay,
не точная симуляция matching engine. Он использует те же сигналы и Risk Manager, но его
модель исполнения по барам отличается от живой PAPER-модели по стакану.

Walk-forward выбирает только `volume_multiple` на train из 1.5/1.7/2.0, затем фиксирует
параметр для test. Все train/test блоки непересекающиеся, также между folds; позиции на
границе закрываются. При менее 10 сделках train сохраняет исходный параметр. Матрица
чувствительности: fee ×1/1.5/2 и slippage ×1/2/4, включая отдельный listing slippage.
Её нельзя использовать для подбора по тестовому периоду и последующего заявления OOS-результата.

Отчёт считает Net PnL, realized PnL, win rate, profit factor, max drawdown, Sharpe по дневным
доходностям (365 дней), expectancy R, среднюю прибыль/убыток, комиссии и проскальзывание.
При отсутствии отрицательных сделок profit factor = null, а не выдуманная бесконечная оценка.
Sharpe не публикуется при менее 30 дневных доходностей; пробелы наблюдений не заполняются
вымышленным нулевым результатом. Статистика с менее 100 сделками или 60 дневными доходностями
маркируется `INSUFFICIENT`. Даже большая выборка не означает доказанную прибыльность.

Для каждой стратегии строится атрибуция капитала «исходный общий бюджет + её realized и
marked PnL»; это помогает сравнить вклады, но не является отдельным независимым капиталом.
Лимиты общие. Бенчмарки на том же оценочном периоде: BTC buy & hold, BTC EMA20/50 и cash,
с расходами. У бенчмарков 100% размещения капитала, у стратегии cap 25%, поэтому сравнивайте
также риск и экспозицию. Нужны медвежьи/боковые периоды, делистинги и затем минимум 30–60
дней PAPER/DEMO. Время с первого запуска панели само по себе не доказывает покрытие данных.

## Тесты и полностью офлайн пример

```bash
pytest -q
ruff check src tests examples dashboard.py
python examples/offline_scenario.py
```

Пример помечен `SYNTHETIC FIXTURE ONLY`. Он создаёт искусственный breakout и бар с пересечением
обоих защитных уровней, чтобы проверить консервативный stop-first. Это намеренно убыточный
механический сценарий, не реальные котировки. Примеры и pytest никогда не отправляют торговые
запросы наружу. Интеграционные тесты используют HTTP mock transport/respx: HMAC, preflight,
тайм-аут после принятия покупки/OCO, отсутствующий ордер, OCO reject → flatten, частичное
защитное исполнение, гонка Kill Switch, комиссии и восстановление. Отдельно проверяется
инвариантность прошлых сделок при изменении будущих свечей.

Streamlit можно проверить без браузера через `streamlit.testing.v1.AppTest` — такой smoke-test
входит в тестовый набор. Результаты фактической проверки поставки: [docs/VALIDATION.md](docs/VALIDATION.md).

## Docker

```bash
cp .env.example .env
mkdir -p data
docker compose build
docker compose run --rm --user root bot chown -R 10001:10001 /app/data
docker compose up -d
docker compose logs -f bot
```

Контейнер исполняется непривилегированным UID 10001; каталог `data` должен быть ему доступен.
На Windows Docker Desktop bind mount обычно управляет правами автоматически. Панель
публикуется только на localhost. `.env`, данные и окружение Python исключены из build context.
В репозитории нет постоянного облачного развёртывания или запущенного торгового сервиса.
